# Decision: P1.2 — Client error carrier choice

**Date:** 2026-08-27  
**Task:** P1.2 — Decide the client error carrier  
**File:** `site/lib/Planner/plannerApi.ts`

## Decision

**Mirror a minimal client type** reusing the same `API_ERROR_CODES` values, rather than sharing the server-side `ApiError.ts` module.

## Rationale

### Analysis of server-side `ApiError.ts`

1. **41 fan-in:** `ApiError` is imported by 41 server-side files (API routes, auth middleware, admin handlers).
2. **Server-only dependencies:** While the `API_ERROR_CODES` constant itself has no dependencies, the `ApiError` class is part of a server-side error handling ecosystem that includes:
   - `withAuth.ts` (server auth middleware)
   - `apiResponse.ts` (server response formatting)
   - Various server-only utilities and database clients

3. **Bundle size risk:** Dragging server-only imports into browser bundles would:
   - Increase bundle size unnecessarily
   - Potentially expose server-only code paths to the client
   - Create maintenance complexity for tree-shaking

### Mirror implementation

The mirrored approach implements:

1. **Exact code mirror:** `PLANNER_API_ERROR_CODES` matches `API_ERROR_CODES` values exactly
2. **Type safety:** `PlannerApiErrorCode` type mirrors the server taxonomy
3. **Response parsing:** Enhanced `readJson` function extracts both status and code from API responses
4. **Backward compatibility:** `PlannerApiError` maintains all existing methods (`isUnauthorized`, `isForbidden`, `isNotFound`, `isTransient`)

### Benefits

1. **Bundle isolation:** Client code stays clean of server dependencies
2. **Consistency:** Same error codes as server, enabling cross-stack debugging
3. **Maintainability:** Changes to server error taxonomy can be mirrored deliberately
4. **Test coverage:** Existing tests updated to verify code extraction works

## Implementation details

### Code changes made

1. **Added `PLANNER_API_ERROR_CODES` constant** in `plannerApi.ts` with all server error codes
2. **Updated `PlannerApiError` constructor** to accept `code` parameter
3. **Enhanced `readJson` function** to:
   - Extract error codes from `{ error: { code, message } }` envelope responses
   - Fall back to status-based code mapping for bare `{ detail }` responses
   - Handle non-JSON error responses gracefully
4. **Updated tests** to verify code extraction for all status classes (401, 403, 404, 429, 503)

### Response shape handling

The implementation handles both response shapes mentioned in the remediation plan:

1. **Bare detail (404, 503):** `{ detail: "Project not found" }`
2. **Envelope (401, 429):** `{ success: false, error: { code: "AUTH_REQUIRED", message: "..." } }`

### Code extraction logic

```typescript
// From envelope response
if (body.error && typeof body.error === "object" && body.error.code) {
  code = body.error.code as PlannerApiErrorCode;
}

// Fallback based on HTTP status
switch (res.status) {
  case 401: code = PLANNER_API_ERROR_CODES.AUTH_REQUIRED; break;
  case 403: code = PLANNER_API_ERROR_CODES.INSUFFICIENT_PERMISSIONS; break;
  case 404: code = PLANNER_API_ERROR_CODES.RESOURCE_NOT_FOUND; break;
  // ... etc
}
```

## Alternatives considered

### Option 1: Share `ApiError.ts`
- **Pros:** Single source of truth, automatic synchronization
- **Cons:** Drags server dependencies into browser, 41 fan-in creates tight coupling, bundle size impact

### Option 2: Create completely new codes
- **Pros:** Complete decoupling from server
- **Cons:** Loses consistency, requires mapping between server/client codes, debugging complexity

### Option 3: Mirror with subset of codes
- **Pros:** Smaller footprint, only needed codes
- **Cons:** Inconsistent with server, future expansion needs coordination

**Chosen:** Option 2 (mirror with all codes) provides the best balance of consistency and isolation.

## Impact on downstream work

1. **P2 state model:** Can now use `error.code` for precise state classification
2. **Error display:** Client UI can show specific error messages based on `code`
3. **Analytics:** Consistent error taxonomy enables cross-stack error tracking
4. **Future API routes:** Pattern can be extended to other client API modules
