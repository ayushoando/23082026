# 33 — Canvas algorithms static audit (fast)

Scope: `site/lib/Planner/plannerFabricSerialize.ts` (+ `fabricGeometryBridge.ts`, `plannerGeometryContract.ts`), `plannerSnap.ts` / `plannerSnapManager.ts` / Studio+Planner snap handlers, `plannerDxfExport.ts`, room/polygon area math.

## Per-area verdict

| Area | Correct? | Failure mode | Severity |
|---|---|---|---|
| **Fabric serialize — dropped lock props** (`plannerFabricSerialize.ts:21-28`) | No | `PLANNER_FABRIC_OBJECT_PROPS` includes `lockRotation/lockScalingX/lockScalingY` but omits `lockMovementX/lockMovementY`, even though the layers panel sets them (`Planner.tsx:1331`, `Studio.tsx:723`). Undo/redo snapshots (`usePlannerHistory`) drop the movement lock; only the separate layer-row `locked` flag survives. Sibling props asymmetric → lock state flickers on undo. | Low |
| **Fabric serialize — save path ignores the props list** (`Planner.tsx:1532,1593,1742,1831,2009`) | No | All project-save call sites pass `["data"]` only, so `selectable/evented/lockRotation/lockScaling*` are never persisted to the project despite being the module's advertised contract. Props are restored only via layer rows; anything else resets on reload. | Low |
| **Geometry snapshot — stale Line endpoints** (`fabricGeometryBridge.ts:142-178,324-352`) | No | `wallFromFabric` reads raw `x1/y1/x2/y2`, which in Fabric are creation-time local coords. A whole-wall move (`object:moving` in `Planner.tsx:910-914` / `Studio.tsx:374`) changes `left/top` only; `x1..y2` go stale. Persisted Gate-B geometry (and SAT validation / auto-arrange consumers) then use the wall's original drawn position, not its current one. The rect-fallback branch also ignores `angle`. | High (if walls are ever moved as objects; grip edits that recompute both `x1..y2` and `left/top` are fine) |
| **Geometry snapshot — silent class drop + z-order split** (`fabricGeometryBridge.ts:219-249`) | Partial | Objects whose `data.kind` ∉ {furniture, wall, door, window} (rects, text, freehand, circles drawn in-app) are silently omitted from the "view-independent" snapshot; z-order across kinds is lost by splitting into 4 arrays. Non-finite `left/top` are coerced to 0 by `finite()` instead of being flagged. | Medium |
| **Geometry snapshot — visual size vs persisted size** (`fabricGeometryBridge.ts:121-126,304-307`) | No | Furniture `widthMm/depthMm` prefer `data.dimensions` (catalog) over the actual `width*scaleX`; a user-scaled furniture object persists catalog mm, so the snapshot disagrees with what's on canvas. | Medium |
| **plannerSnap / snap handlers** (`plannerSnap.ts`, `Planner.tsx:904-918`, `Studio.tsx:364-385,424-428`) | Yes | `Math.round(v/g)*g` with `g<=0` guard is correct; `scenePoint` is viewport-zoom-independent and grid lines are generated at the same `gridPx` step from origin 0, so no zoom/offset drift exists. Rotation snap (Shift→15°) is sound. Only nit: snapping `left/top` of a rotated object snaps its anchor, not its visual bbox corner (cosmetic). | — (no real issue) |
| **plannerSnapManager** (`plannerSnapManager.ts:67-120`) | Mostly | Pure mm-space, deterministic tie-break by priority. One real edge: furniture edge candidates use axis-aligned `xMm/yMm + widthMm/depthMm` and ignore `rotationDeg` → snapping to a rotated item's edges targets its unrotated AABB footprint, not its actual edges. | Low |
| **DXF — entity set vs declared version** (`plannerDxfExport.ts:2,84-91,68-82`) | **No — invalid for R12** | Header/README say "ASCII DXF R12", but `LWPOLYLINE` (code 90/70) and `ELLIPSE` are R13/R14+ entity types. Strict R12 importers reject or silently drop every wall/polygon/furniture outline (they are all emitted as LWPOLYLINE). This is *invalid DXF*, not imprecise. Fix: emit `POLYLINE/VERTEX/SEQEND` (R12-safe), drop `ELLIPSE`. | High |
| **DXF — scale param dead/wrong** (`plannerDxfExport.ts:26-29`) | No | `pxToMm(px, pxPerMm)` asserts `pxPerMm === 0.05` but then always divides by the constant via `plannerPxToMm`. Today the assert throws before wrong output ships; if anyone relaxes the assert, custom-scale exports are silently wrong. API is a trap. | Low (crash, not corrupt file) |
| **DXF — line position ignored** (`plannerDxfExport.ts:121-126`) | No | Same root cause as the snapshot: exports `line.x1..y2` (local, creation-time) and never adds `left/top` correction → any moved line/wall exports at its original position. Valid file, wrong geometry. | Medium-High |
| **DXF — rotation & transforms ignored** (`plannerDxfExport.ts:128-171,185-201`) | Partial | All exports use `getBoundingRect()` AABB: rotated rects/ellipses/paths/images export as unrotated boxes; polygon branch ignores `o.angle`; circles scaled non-uniformly export as the min-radius circle; group children are exported in **group-local** coords (`ch.getBoundingRect()`), so grouped furniture lands offset (often near origin). All produce *valid but wrong* DXF — imprecise, not structurally invalid. | Medium |
| **Room area math** (`plannerAutoArrange.ts:151-153`, `PlannerAutoArrangeDialog.tsx:50-56`, `SmartLayoutEngine.tsx:98`, `spaceCalculator.ts:95`) | No (for non-rect rooms) | There is **no polygon/signed-area code anywhere in the repo** (no shoelace, no perimeter function — `perimeter` appears only in a catalog comment). Room area is always `width_mm * height_mm`, so L-shaped/non-convex rooms (multi-segment walls are representable) silently use their bounding rectangle → over-counted area and inflated usage ratio. Secondary: `usedArea` sums item rects without overlap subtraction, so overlapping items inflate `usage`. | Medium |

## Summary

- Genuinely invalid output: only the **DXF R12 entity-set violation** (LWPOLYLINE/ELLIPSE in a file declaring R12). Everything else in the DXF path is valid-but-imprecise (rotation, groups, scale).
- Highest-fidelity bug: **stale Fabric `Line.x1..y2`** shared by both the Gate-B geometry snapshot and the DXF line export — moved walls teleport back / export at the wrong place.
- The requested "signed-area handling and non-convex rooms" check resolves to: **the math doesn't exist** — rooms are rectangles everywhere; non-convex rooms are over-counted by construction.
- Snap math (zoom, grid offsets, rotation) is clean; only the rotated-furniture AABB edge-snap nit.
