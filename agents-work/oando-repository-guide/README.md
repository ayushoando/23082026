# Oando repository guide

A short, curated map of the repository: the four surfaces, the data ownership, the agent process, and where every durable fact lives. This guide is intentionally small — **four authored files** — because the detail it used to duplicate is already owned elsewhere:

- `./AGENTS.md` — process floor: authority order, layout, persistence, protected commands, traps.
- `./Agents/INDEX.md` + handbooks `01`–`07` — task procedures (standard, testing, browser, failures, docs, architecture, CSS).
- `./docs/architecture/`, `./docs/database/`, `./docs/governance/` — durable reference; live code wins on mismatch.
- `./agents-work/repository-map/index.html` — generated whole-repository map with live graph evidence.
- `./generated-documents/` — generated docs and data from the tech-docs generator.

The Markdown under `./markdown/` is the authored source; the `html/` projection is regenerated by the tech-docs pipeline (`node tech-docs-generator/scripts/generate-all.mjs`) — never hand-edit generated HTML.

## First five facts

1. Four surfaces: Marketing (`/`), Admin (`/admin/*`), Furniture Studio (`/oostudio`), Floor Planner (`/ooplanner`).
2. Planner and Studio are forked applications. They never import each other.
3. Products Supabase owns marketing catalog/configurator data. Admin Supabase owns staff, customers, plans, furniture, and descriptors.
4. Production filesystem is read-only. Runtime writes use mode-aware persistence wrappers, not raw disk helpers.
5. Run `pnpm` from the repository root. There is no product `site/package.json`.

## Begin Here

Start with one ordinary-language sentence describing the desired outcome — no path, package, skill, or mode vocabulary required. Before any modification, the agent applies the authority order (`current user instruction → live code and fresh command output → ./AGENTS.md → ./Agents/ → ./docs/`, then `./plans/README.md` for active coordination) and works through:

1. Restate the outcome with an action verb and the inferred surface or domain; define specialized terms before requesting a decision.
2. Select exact first evidence locations and explain why each is first. Never guess a path.
3. Select one D01–D22 row from the [task-classifier](#task-classifier-table) below, or D22 when the topic is unfamiliar.
4. Select every matching user-global opencode skill (`oando-repo-map`, `oando-testing`, `oando-focss-css`, `oando-databases`, `oando-browser-ui`); reject non-matches with reasons; use Local Evidence when nothing matches. Skills are routing aids, not runtime switches.
5. Choose `Vibe`, `Plan`, `Spec`, `Autopilot`, or `Supervised` from risk and scope.
6. Classify every proposed command: `read-only inspection`, `Normal-Agent Eligible Check`, `Protected Command`, or `no-run pending authorization`. Tests, gates, builds, browser checks, and coverage require exact current-session authorization per `./AGENTS.md`.
7. For an Output-Producing Task: declare Artifact Class, exact approved output home, filename pattern, owning source/script, authored-or-generated state, and rejected placements. Apply the Site Write Gate before any `./site/` write.
8. Request only unavoidable Owner Decisions. If safe modification facts are missing, choose read-only discovery instead.

## Surface Status and Coverage-Gap Admission

Use only `wired`, `demo/local-only`, `present-but-unverified`, `unwired/absent`, or `legacy`. Every status names Evidence Source, Current Owner, Next Action, and Evidence Limitation. Do not transfer a status between Planner and Studio, between the CRM demo and customer queries, or between a local disk path and hosted Supabase.

```text
Coverage-Gap Admission Card
Named Area or Capability:
Status:
Evidence Sources Checked:
Evidence Limitation:
Next Evidence Source:
Owner Action:
Scope Boundary:
Next Decision:
```

Do not call an area wired or complete without End-to-End Evidence. A Coverage-Gap Admission is not a True Blocker; an evidenced True Blocker belongs only in root `./Failures.md`.

## Artifact placement

| Output | Approved home | Prohibited home |
|---|---|---|
| Agent-authored report/work product | `./agents-work/<workstream>/<report-type>/` or approved `./agents-work/oando-repository-guide/` | `./agents-work/` root, `./results/`, `./site/` |
| Command-generated Machine Evidence | `./results/<purpose>/`, such as `./results/tests/`, `./results/site/`, `./results/ops/` | `./results/` root, `./agents-work/`, `./site/` |
| Tech-docs generator output | `./generated-documents/` | `./results/`, `./agents-work/`, `./site/` |
| Active plan material | `./plans/<name>/` indexed by `./plans/README.md` | `./results/`, `./site/`, unowned root |
| Agent skills | User-global opencode configuration (`~/.config/opencode/`), outside this repository | `./site/`, `./results/`, `./agents-work/` |
| True Blocker | Root `./Failures.md`; supporting authored analysis in approved `./agents-work/<workstream>/<report-type>/` | Duplicate ledgers |
| Product source | Approved product source; `./site/` only for an approved Core Product Write | `./site/` for reports, skills, results, prompts, plans, or generated files |

**Locked Path Gate:** direct root files, `./docs/**`, and `./Agents/**` are read-only evidence unless the Repository Owner explicitly names and authorizes that exact file in the current request; a read permission never becomes write/delete permission, and a copy never proves a locked source changed. `./agents-work/` is distinct from `./Agents/`.

**Site Write Gate:** before any `./site/` write, classify the target as an explicitly approved Core Product Write (exact outcome, owned paths, matching skills, expected evidence) or a Non-Core Artifact, which is stopped and redirected to its approved non-site home.

## Plain-Language Response Contract

Every task-start, progress, handoff, pause, and completion response uses this field order: **Outcome; Known; Unverified; Exact First Evidence Locations; Selected Skills; Rejected Skills and Reasons; Numbered Next Actions; Likely Files or Areas; Risk; Allowed Checks; Protected or Pending Checks; Exact Completion Proof; Unavoidable Owner Decisions.** Missing proof remains `pending`, `blocked`, or `not-observed`; it is never silently promoted to pass, wired, complete, runtime, rendered, hosted, or relocated.

A **Completion Record** repeats the selected and rejected skills from the Route Record, the changed scope (or inspected scope when nothing changed), exact observed evidence, pending validation with the exact command and authorization limitation, Coverage-Gap Admissions, Separate Approval Work, True Blockers, next owner, and status. A command name, plan, or prose rule is not a command result.

## Multi-agent rule

At most four agents, disjoint file ownership, serial integration; never worktrees. Shared paths, terminology, handoffs, and integration are serial.
